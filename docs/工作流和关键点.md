# SchemaRAG Dify Plugin：项目流程、业务逻辑与关键点位

本文用于从“整体架构 + 端到端调用链路”的角度，梳理本仓库的业务流程、模块职责以及关键控制点（安全/稳定性/成本）。

## 1. 架构总览

### 1.1 核心分层

- **Provider（插件提供方）**：负责插件安装后的凭据校验与 SchemaRAG 初始化（构建/上传 schema 知识库）。
  - 入口：`provider/build_schema_rag.py::SchemaRAGBuilderProvider`
  - 配置：`provider/provider.yaml`
- **Tools（工具节点）**：工作流/对话中被调用的“能力单元”，核心是 `text2data`（端到端）。
  - 主要工具：`tools/text2data.py` / `tools/text2sql.py` / `tools/sql_executer.py`
- **Service（服务层）**：承载复用逻辑（知识库检索、DB访问、refiner、缓存、上下文）。
  - `service/knowledge_service.py`：Dify 知识库检索（支持多知识库并发 + 缓存）
  - `service/database_service.py`：SQLAlchemy 统一执行查询
  - `service/sql_refiner.py`：LLM 反馈循环的 SQL 自动修复
  - `service/context/*`：对话记忆
  - `service/cache/*`：通用缓存体系
- **Core（底层能力）**：schema 抽取与表示、绘图模块等。
  - `core/m_schema/schema_engine.py`：从 DB 抽取表/字段/注释/示例等，生成 mschema 文本

### 1.2 入口与启动

- 运行入口：`main.py`（由 dify-plugin 框架启动）
- Provider 注册：`provider/provider.yaml` 的 `extra.python.source` / `provider`
- 工具注册：`provider/provider.yaml` 的 `tools:` 列表引用 `tools/*.yaml`

## 2. 两条主线流程

### 2.1 插件初始化/建库主线（Provider → SchemaRAGBuilder）

发生时机：用户在 Dify 插件配置页填写凭据并保存（或平台触发校验）。

1. `SchemaRAGBuilderProvider._validate_credentials(credentials)`
  - 校验 `api_uri`、`dataset_api_key`、`db_type`、`db_host`/`db_user`/`db_password`/`db_name` 等必填项
2. `_build_schema_rag(credentials)`
  - 组装 `DatabaseConfig` + `LoggerConfig` + `DifyUploadConfig`
  - 可选解析 `tables_name` → `include_tables`
3. `SchemaRAGBuilder.generate_dictionary()`
  - `SchemaEngine` 抽取 schema，生成 mschema 字符串
4. `SchemaRAGBuilder.upload_text_to_dify(dataset_name, schema_content)`
  - 将 mschema 文本上传至 Dify 知识库（dataset）

关键文件：

- `provider/build_schema_rag.py`
- `service/schema_builder.py`
- `core/m_schema/schema_engine.py`

### 2.2 业务调用/问答主线（Tool → Service → DB/LLM）

发生时机：工作流/对话节点调用工具。

推荐端到端：`tools/text2data.py::Text2DataTool`（集成检索 + 生成 + 执行 + 可选修复 + 输出）。

## 3. 端到端业务链路：Text2Data（最重要）

文件：`tools/text2data.py`，核心方法：`Text2DataTool._invoke()`

### 3.1 输入与参数

输入（工具参数）典型包含：

- `dataset_id`：schema 知识库 id（支持逗号分隔多个）
- `example_dataset_id`：示例 SQL 知识库（可选）
- `content`：用户问题（最大长度 `MAX_CONTENT_LENGTH=10000`）
- `llm`：用于生成 SQL / summary 的模型配置
- `dialect`：方言（mysql/postgresql/mssql/oracle/dameng/...）
- `top_k` / `retrieval_model`：检索策略
- `output_format`：json/md/summary
- `max_rows`：最大返回行数（默认 500）
- `enable_refiner` / `max_refine_iterations`：SQL 自动修复开关与迭代上限

### 3.2 主流程（按执行顺序）

1. **参数与配置校验**
  - 校验 `dataset_id/content/llm` 必填
  - 校验 provider 侧 DB 凭据完整性
2. **schema 检索（多知识库）**
  - `KnowledgeService.retrieve_schema_from_multiple_datasets(dataset_id, content, top_k, retrieval_model)`
  - 多 dataset 时：异步并发请求 `/datasets/{id}/retrieve`，最终拼接为多段 `=== 知识库 {id} === ...`
3. **可选：示例知识库检索**
  - `example_dataset_id` 同样走多知识库检索
4. **构建 Prompt 并调用 LLM 生成 SQL（流式）**
  - Prompt：`prompt/text2sql_prompt.py`
  - LLM 调用：`self.session.model.llm.invoke(..., stream=True)`，中间过程用 `<think>` 折叠输出
5. **SQL 清洗与安全校验**
  - `utils._clean_and_validate_sql(sql_query)`
  - 黑名单正则：禁 DDL/DML、存储过程执行、文件读写、延迟函数、敏感系统信息等
6. **执行 SQL**
  - `DatabaseService.execute_query(...)`（SQLAlchemy）
  - `max_rows` 截断，数值格式化避免科学计数法：`format_numeric_values()`
7. **可选：SQL Refiner 自动修复**
  - 仅当执行失败且 `enable_refiner=True`：
    - `SQLRefiner.refine_sql()`：执行“验证查询/错误反馈/LLM修复”迭代
    - 修复成功后再次执行修复 SQL
8. **输出格式**
  - `summary`：先转 json，再用 `prompt/summary_prompt.py` 生成摘要（流式）
  - 其它：`DatabaseService._format_output(..., json/md)`

## 4. Schema 抽取与 mschema 生成（SchemaEngine）

文件：`core/m_schema/schema_engine.py`

### 4.1 抽取内容

- 表：表名、表注释
- 字段：字段名、类型、注释、nullable、default、autoincrement、是否主键
- 关系：外键（含 referenced schema/table/column）
- 示例：对字段做 `SELECT DISTINCT ... LIMIT n` 抽样（默认 5）
  - `utils.examples_to_str()` 会过滤疑似 email、URL 等内容，降低泄露风险

### 4.2 多数据库差异处理要点

- MySQL/Doris：数据库名作为 schema（避免跨库拉全量表）
- PostgreSQL：默认 `public`
- MSSQL：默认 `dbo`
- 达梦：db_name 映射为 schema（并且连接建立后执行 `ALTER SESSION SET CURRENT_SCHEMA = "{dbname}"`）

## 5. 缓存与上下文（性能/体验关键点）

### 5.1 知识库检索缓存（schema_cache）

文件：`service/knowledge_service.py`

- `retrieve_schema_from_dataset()` 使用 `@cacheable(name="schema_cache", ttl=3600)`
- 缓存键基于：`dataset_id + normalize_query(query) + top_k + retrieval_model`
- 多知识库并发检索本质上仍依赖单库检索缓存提升命中率

### 5.2 SQL 生成缓存（sql_cache）与对话记忆（ContextManager）

文件：`tools/text2sql.py` / `service/context/context_manager.py`

- `text2sql` 支持：
  - **sql_cache（LRU，2h）**：命中则直接返回缓存 SQL
  - **对话记忆**：按 `user_id:tool_name` 存储 query/sql，默认窗口 3、过期 24h
  - `reset_memory`：清空该用户对话历史

> 注：`text2data` 目前不接入 ContextManager（其逻辑更偏“一次性端到端”），主要依赖 schema 检索与 DB 连接等复用。

## 6. SQL 安全与稳定性关键点（必须关注）

### 6.1 主要安全闸门：SQL 清洗与危险操作拦截

文件：`utils.py::_clean_and_validate_sql()`

- 黑名单模式，主要禁止：
  - DDL/DML：drop/delete/truncate/update/insert/create/alter/grant/revoke
  - 存储过程/扩展：exec/execute/sp_/xp_
  - 文件读写：into outfile / load_file / load data
  - SELECT INTO 等潜在写入
  - `sleep`/`waitfor` 等延迟
  - `@@` 与部分 `information_schema` 访问

### 6.2 关键风险点（现状）

1. `**DatabaseService.execute_query()` 本身并不限制只读**
  - 若调用方绕过 `_clean_and_validate_sql()`，理论上可执行非 SELECT（尽管工具通常会先清洗校验）。
2. `**Text2DataTool` Refiner 成功后执行 `refined_sql` 前未再次做 `_clean_and_validate_sql()`**
  - 目前流程：LLM 修复 SQL → 直接执行
  - 这会把“安全策略”从“硬闸门”变为“依赖 prompt 约束”，属于需要重点标记的点位。

### 6.3 成本与超时控制点

- 检索 API 超时：30s（requests/httpx）
- Refiner：多次 DB 验证 + LLM 调用，会显著增加延迟与 token 消耗
- 结果行数：`max_rows` 截断，避免大结果导致内存与输出成本爆炸

## 7. 扩展点位（后续改造最常落点）

- **新增数据库支持**
  - `service/database_service.py::DB_DRIVERS`
  - `config.py` 的连接串规则（如有）

  - 在 `provider/provider.yaml` 的 `tools:` 注册
- **Prompt 调优**
  - `prompt/text2sql_prompt.py` / `prompt/sql_refiner_prompt.py` / `prompt/summary_prompt.py`
- **缓存策略**
  - `service/cache/`*：可扩展 TTLCache/LRUCache 配置、统一初始化策略、统计/清理
- **安全增强**
  - 把 “只允许 SELECT” 做成 DB 层硬限制（例如执行前解析语句类型）
  - Refiner 输出执行前强制二次 `_clean_and_validate_sql()`

---

## 8. 一句话总结

本插件将“数据库 schema 抽取 → 上传为 Dify 知识库 → 检索相关 schema → LLM 生成 SQL → 安全清洗 → SQLAlchemy 执行 →（可选）LLM 纠错 → 格式化/摘要/可视化”封装成可编排工具节点；其中最关键点位是 **schema 检索拼接策略、prompt 组织方式、SQL 安全闸门、Refiner 迭代闭环、缓存/上下文对质量与成本的影响**。
